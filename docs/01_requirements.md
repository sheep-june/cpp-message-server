## 1. プロジェクト概要

### 1.1 目的

本プロジェクトは、C/C++を用いたメッセージ処理およびタスクスケジューリングサーバーの開発を目的とする。

クライアントから受信したメッセージを解析し、タスクの登録、管理、優先順位に基づく処理、実行結果の返却を行う。

また、JSONとBinaryの相互変換、TCP/IP通信、データ構造とアルゴリズム、CMakeによるビルド、GoogleTestによるテスト、Podmanによるコンテナ化を段階的に実装する。

### 1.2 開発目標

- C/C++によるプログラミング能力の向上
- C言語とC++の混在プロジェクトの構築
- CMakeによるビルドシステムの理解
- JSONとBinaryのシリアライズ・デシリアライズ
- TCP/IPを使用したサーバー・クライアント通信
- データ構造とアルゴリズムの実践
- Linux環境でのアプリケーション実行
- Podmanによるコンテナ化
- GoogleTestを用いた自動テスト
- GitHubによるソースコード・設計書の管理

## 2. システム概要

本システムでは、クライアントから送信されたメッセージをサーバーが受信し、メッセージの種類に応じた処理を実行する。

主な処理の流れは以下のとおりとする。

1. クライアントがメッセージまたはタスクを送信する。
2. サーバーがメッセージを受信する。
3. メッセージ形式および入力内容を検証する。
4. 必要に応じてJSONとBinaryを相互変換する。
5. タスクを登録し、キューで管理する。
6. タスクの優先順位に従って処理する。
7. タスクの状態および実行結果を管理する。
8. クライアントからの照会要求に対して結果を返却する。

初期段階ではネットワーク通信を使用せず、ローカルプログラム内で処理を実行する。

## 3. 機能要件

### FR-01 メッセージ管理

- メッセージの作成
- メッセージIDの管理
- メッセージ種別の判定
- メッセージ内容の検証
- 不正なメッセージの検出

### FR-02 データ変換

- JSONから内部データへの変換
- 内部データからJSONへの変換
- 内部データからBinaryへの変換
- Binaryから内部データへの復元
- データ長および値の範囲検証

※ Binaryのフォーマットは独自に定義する。

### FR-03 タスク管理

- タスクの登録
- タスクIDによる照会
- タスクのキャンセル
- タスク状態の管理
- 実行結果の取得

タスク状態は初期案として以下を使用する。

| 状態 | 説明 |
|---|---|
| PENDING | 実行待ち |
| RUNNING | 実行中 |
| COMPLETED | 正常終了 |
| FAILED | 異常終了 |
| CANCELLED | キャンセル |

### FR-04 タスクスケジューリング

- FIFO方式によるタスク処理
- 優先順位に基づくタスク処理
- 同一優先順位における登録順の維持
- タスク実行順序の管理

### FR-05 TCP通信

- TCPサーバーの起動
- TCPクライアントからの接続
- メッセージ送受信
- 接続終了処理
- 通信エラー処理
- メッセージ境界および受信データ長の管理

### FR-06 アルゴリズム

基本機能として以下を実装する。

- Queue：FIFOによるタスク管理
- Hash Map：IDによるタスク検索
- Priority Queue：優先順位によるタスク選択
- Sliding Window：一定期間の処理件数集計

拡張機能として以下を検討する。

- Binary Search：ソート済み履歴の検索
- BFS / DFS：タスク依存関係の探索
- Topological Sort：依存関係に基づく実行順序決定
- Union-Find：グループ管理機能への応用

### FR-07 テスト

- 単体テスト
- JSON/Binary変換の往復テスト
- 異常データの入力テスト
- タスクの実行順序テスト
- 通信テスト
- 境界値テスト

### FR-08 コンテナ実行

- Podmanによるコンテナイメージ作成
- Linuxコンテナ上でのアプリケーション実行
- ネットワークポートの設定
- コンテナログの確認
- コンテナの起動・停止・削除

## 4. 非機能要件

| 分類 | 要件 |
|---|---|
| 保守性 | 機能単位でソースファイルを分割する |
| 可読性 | 命名規則を統一し、必要なコメントを記載する |
| 移植性 | macOSおよびLinuxでのビルドを目標とする |
| 信頼性 | 不正な入力によってサーバーが異常終了しないようにする |
| テスト性 | データ変換とタスク処理を独立してテスト可能にする |
| 拡張性 | 通信機能と処理ロジックを分離する |
| 性能 | 処理件数および処理時間を測定可能にする |

具体的な性能目標値は、基本機能の実装後にベンチマーク結果を基に設定する。

## 5. 開発対象外

初期バージョンでは以下の機能を開発対象外とする。

- ユーザー認証・権限管理
- 外部データベース
- 分散サーバー構成
- インターネットへの公開運用
- 高可用性クラスタ
- Webフロントエンド

必要に応じて将来的な拡張を検討する。

## 7. 初期MVP完了条件

初期MVPでは、以下の項目がすべて満たされていることを完了条件とする。

- CMakeでC/C++ソースコードをビルドできる。
- C言語で定義したメッセージデータをC++から利用できる。
- メッセージの登録・取得ができる。
- JSONとBinaryを相互変換できる。
- 変換前後の主要データが一致する。
- 異常な入力に対してエラーを返す。
- 主要処理の単体テストが成功する。

TCP通信およびコンテナ化は初期MVP完了後の拡張対象とする。
