## 1. システム構成

### 1.1 基本方針

本システムは、C/C++によるメッセージ処理とタスクスケジューリングを実行するサーバーアプリケーションとする。

初期段階では、ローカル環境で動作する単一プロセスのプログラムとして開発する。

その後、TCP通信機能を追加し、Linuxコンテナ上で動作するサーバーへ拡張する。

以下の設計方針を採用する。

- 通信処理とビジネスロジックを分離する。
- データ変換処理を独立したモジュールとする。
- C言語とC++の両方を使用する。
- CMakeによるモジュール単位のビルド構成とする。
- テスト可能なインターフェースを設計する。
- 機能を段階的に追加できる構成とする。

## 2. システムアーキテクチャ

### 2.1 最終構成

```text
+-------------------------------+
|         C++ Client            |
|  Message / Task Request       |
+---------------+---------------+
                |
                | TCP/IP
                v
+-------------------------------+
|         TCP Server            |
|  Connection / Request Handler |
+---------------+---------------+
                |
                v
+-------------------------------+
|       Message Processor       |
|   Validation / Dispatching    |
+---------------+---------------+
                |
       +--------+--------+
       |                 |
       v                 v
+--------------+  +------------------+
| JSON/Binary  |  |  Task Manager    |
| Converter    |  |                  |
+--------------+  +--------+---------+
                           |
                           v
                  +------------------+
                  |  Task Scheduler  |
                  | Queue / Priority |
                  +--------+---------+
                           |
                           v
                  +------------------+
                  |  Task Executor   |
                  | Result / Status  |
                  +------------------+
```

本図は最終構成の概念図であり、初期段階ですべてのモジュールを実装するものではない。

JSON/Binary変換モジュールは、メッセージのエンコード・デコードを担当する共通機能とする。

## 4. データ設計

### 4.1 メッセージデータ

初期段階では以下の項目を持つメッセージを扱う。

| 項目 | 型（論理型） | 説明 |
|---|---|---|
| messageId | 整数 | メッセージ識別子 |
| type | 文字列 | メッセージ種別 |
| priority | 整数 | 優先順位 |
| payload | 文字列 | 処理対象データ |

JSON形式の例：

```json
{
  "messageId": 1001,
  "type": "TASK",
  "priority": 2,
  "payload": "process-data"
}
```

メッセージIDの採番方式、項目の最大長、値の範囲は詳細設計で決定する。

### 4.2 Binary形式

Binaryデータは、独自に定義した固定的な通信仕様に従って生成する。

以下の項目を詳細設計で定義する。

- ヘッダー構造
- フィールドの配置順序
- フィールド長
- 数値のバイトオーダー
- 文字列のエンコーディング
- データ全体の長さ
- フォーマットバージョン
- 不正データの検出方法

C構造体のメモリ領域を、そのまま外部通信データとして使用しない。

構造体のパディングや環境依存のデータ表現を避けるため、各フィールドを明示的にエンコードする。

## 5. タスク管理設計

### 5.1 タスク状態

タスクの状態は以下とする。

| 状態 | 内容 |
|---|---|
| PENDING | 実行待ち |
| RUNNING | 実行中 |
| COMPLETED | 正常終了 |
| FAILED | 異常終了 |
| CANCELLED | キャンセル |

基本的な状態遷移は以下を想定する。

```text
PENDING
   |
   +----> RUNNING ----> COMPLETED
   |          |
   |          +-------> FAILED
   |
   +----> CANCELLED
```

初期実装では、実行前のタスクのみキャンセル可能とする。

### 5.2 データ管理

タスク管理には、C++標準ライブラリのデータ構造を使用する。

| データ構造 | 使用目的 |
|---|---|
| std::queue | FIFOによる処理待ち管理 |
| std::unordered_map | タスクIDによる検索 |
| std::priority_queue | 優先順位による実行対象の選択 |
| std::vector | タスク履歴・一覧管理 |

実行待ちキューの選択方式は開発段階に応じて切り替える。

## 6. スケジューリング設計

### 6.1 初期方式

初期バージョンではFIFO方式によるタスク処理を実装する。

登録された順序に従ってタスクを実行する。

### 6.2 優先順位方式

拡張段階では優先度付きキューを使用する。

優先順位が同じ場合は、登録順序を優先する。

### 6.3 依存関係方式

高度なアルゴリズムの実装段階では、タスク間の依存関係を追加する。

- BFS / DFSによる依存関係の探索
- 循環依存の検出
- トポロジカルソートによる実行順序の決定

依存関係が存在する場合、優先順位よりも実行可能条件を優先する。

## 7. 通信設計

### 7.1 通信方式

TCP/IPによるクライアント・サーバー方式とする。

初期のネットワーク実装では、単一クライアントからの接続を処理する構成とする。

その後、複数クライアントへの対応を検討する。

### 7.2 基本処理フロー

1. サーバーを起動する。
2. 指定ポートで接続を待機する。
3. クライアントが接続する。
4. メッセージを受信する。
5. メッセージを検証する。
6. メッセージ内容に応じた処理を実行する。
7. 応答メッセージを送信する。
8. 接続状態を管理する。

### 7.3 通信上の考慮事項

- TCPの受信データにはメッセージ境界が保証されない。
- 1回の受信処理でメッセージ全体を取得できるとは限らない。
- 送信処理も部分送信を考慮する。
- 受信サイズの上限を設ける。
- タイムアウトおよび異常切断を処理する。

具体的な通信フォーマットは通信仕様書で定義する。
